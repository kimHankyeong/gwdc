## 수정 우선순위

### P1 — 판매처 식별을 신뢰되지 않은 이름으로 판정
- `backend/src/search.ts:52`는 페이지 JSON-LD의 offers.seller.name을 merchant로 사용한다.
- `backend/src/workflow.ts:97`은 이 값을 URL hostname보다 우선하고 Python이 allowedMerchants와 비교한다.
- 격리된 파서/Python 재현: 출처를 attacker.example로 가정한 fixture에서 seller.name=trusted.example, allowedMerchants=[trusted.example] → allowed=true.
- 실제 사이트 공격이나 SSRF 우회까지 검증한 것은 아니다. 수집 허용 출처에 올라온 임의 판매자 이름을 신뢰하는 판정 경로의 결함이다.
- 조치: 검증한 출처/판매처 ID 매핑을 Hard 판정에 사용. 페이지 이름은 표시용으로만 보관. 식별 미확인 시 UNKNOWN/차단.

### P1 — 감사 실행 준비 상태가 주문 실행 선행조건에 연결되지 않음
- `backend/src/agent.ts:117`부터의 prepare는 payload 지원 범위만 확인하고 실제 감사 서비스 준비 상태를 확인하지 않는다.
- `purchaseWorker.ts`는 감사 설정 없이도 모의 차감/영수증/audit job을 commit할 수 있다. 기존 DB 시험에서도 외부 설정 없이 이 경로를 실행한다.
- `auditWorker.ts`는 미설정이면 작업을 처리하지 않는다. 이후 미완료 감사 때문에 정책 편집과 해당 실행의 안전 취소가 막힐 수 있다.
- 조치: 실제 감사가 필수인 주문은 감사 서비스 capability 확인 후 허용. 정상 설정 후 일시 장애는 기존 복구 경로로 처리.

### P1 — 재개 컨텍스트와 단계 계약이 불완전
- `backend/src/agent.ts:20`의 재개 입력에 constraint_approval, evaluations, question이 없다. 승인/교육 예시 수행 사실을 모델에 명시적으로 전달하지 않는다.
- Tool마다 일부 선행조건은 있지만 공통 allowedStages/output schema 검증은 없다. 예를 들어 ask_clarification은 active 여부만으로 상태를 NEEDS_INPUT으로 덮는다.
- 이는 코드 검토 결과이며 이번 UI QA에서 중복 주문이 발생한 것은 아니다.
- 조치: 최소 현재 업무 상태에 승인/평가/미해소 질문 포함, 단계별 허용 Tool과 결과 schema를 서버에서 강제.

### P2 — 사용자 흐름 및 정책 표시 누락
- 거래 화면에 읽기 전용 정책 원문/유효기간/잔여 예산을 표시하는 PolicyViewer가 없다.
- 후보 선택·모의 입력·평가·최종 승인에 원시 JSON, 평가 ID, intent ID 입력이 필요하다.
- 배송 속도/리뷰 우선순위 등의 명세 필드가 구매 조건 schema/UI에 없다. 배송 속도는 Python 평가에도 없다.
- 조치: 정책/후보/예시/최종 견적을 사람이 확인할 수 있는 항목으로 표시하고 내부 ID는 UI가 연결. 미지원 조건을 명시.

### P2 — 검색 실패 안내와 언어 불일치 (실제 UI 재현)
- 한국어로 사무용 노트 1개/5,000원/실제 검색을 요청 → 예시 확인·조건 승인 → 재개.
- state=NEEDS_INPUT, questionKey=search_blocked. 중국어로 모의 예시 전환을 제안하며 사용자가 지정하지 않은 브랜드 제외 예시를 포함했다.
- candidates/intents/receipts는 모두 빈 목록이었다. 가짜 주문 실행은 관찰되지 않았다.
- 조치: SEARCH_NOT_CONFIGURED 등 환경 오류는 한국어 서버 상태로 직접 표시. 모델이 장애 복구 방법·상품 사실을 대신 지어내지 않도록 차단.

### P2 — 검색 공급자 응답 검증 및 수집 계약 부족
- `backend/src/search.ts:79`: 격리된 fetch fixture가 HTTP 200 + `{}`를 반환하면 오류 대신 `[]`를 반환했다.
- country/search_lang/cursor/offset 및 more_results_available 처리가 없고 첫 10개만 요청한다.
- 범용 JSON-LD만 처리하며 도메인별 파서 검증·필드별 근거 계약이 충분하지 않다.
- 조치: 실제 정상 빈 결과와 malformed 응답을 schema로 구분하고 필요한 페이지네이션/출처 검증 구현.

### P2 — 미설정 서비스 오류가 사용자에게 파싱 오류로 노출
- 정책 변경 시작 클릭 → `Failed to execute 'json' on 'Response': Unexpected end of JSON input`.
- `frontend/src/main.ts:16`이 오류 응답도 무조건 JSON으로 읽는다. 별도 정책 서비스가 필요하다는 안내가 없다.
- 조치: 상태 코드/Content-Type/빈 본문 처리, 서비스 준비 상태 표시. API 실패 후에도 서버의 최신 실행 상태를 조회.
